# 06 本地开发与目录关系

## 目录关系：并列，不要嵌套

```
C:\Users\admin\Desktop\scratch-test\
├── deepseek-harness\          # harness 检出（只读地跑、只用来启动）
│   ├── packages\  apps\  ...
│   └── node_modules\          # 仓库自己的依赖，已 pnpm install + build
└── dsh-duck-analytics\        # 插件仓库（独立 git，独立 pnpm）
    ├── src\  lib\  test\  docs\
    └── node_modules\          # 插件自己的 devDependencies
```

三条理由：

1. **两个 git 仓库**。插件不复用 harness 的提交历史，harness 也不该看到插件的改动。
2. **插件不能依赖 `../packages`**。DSH 包走 `peerDependencies`（运行时用宿主的副本）+ `devDependencies`（类型检查与测试），因此两边各自 `install` 就能工作。
3. **别人能装**。插件用 `dsh.bundle` + `cordis.patch.yml` 分发，行按包名引用；放在 harness 仓库里的目录只能靠绝对路径 `--patch`，没法给别人用。

多个插件就用兄弟目录并列，不要在 harness 里建 `plugins/`。

## 两种回路

### A. 装进 profile（推荐，最接近真实使用）

```sh
cd C:\Users\admin\Desktop\scratch-test\deepseek-harness
node apps/cli/lib/bin.js plugin --profile duck add 'file:C:\Users\admin\Desktop\scratch-test\dsh-duck-analytics'
node apps/cli/lib/bin.js --profile duck            # 启动（web 同名子命令）
```

- profile 目录在 `%USERPROFILE%\.dsh\profiles\duck`，`add` 把参数原样转给 profile 里的 pnpm；`file:` 链接保留插件自己的 `node_modules`。
- 插件的 `cordis.patch.yml` 作为 bundle 层被应用，`--dump-config` 里能看到 `# == dsh-duck-analytics`。
- **peer 依赖由宿主提供**：运行时用的是 harness 自己的 `@deepseek-ai/dsh-tools` 等，因此 `HarnessError` 的 `instanceof` 成立，工具错误码不会丢。

### B. `--patch` 覆盖层（最快，适合改一行看一行）

```sh
cd C:\Users\admin\Desktop\scratch-test\deepseek-harness
pnpm dsh web --patch ./dsh-duck-analytics/cordis.yml
```

- `cordis.yml` 是**机器本地**的 overlay，行按绝对路径指向 `lib/index.js`；不用装 profile，也不污染 `~/.dsh`。
- 代价：行是路径条目，插件按自己的 `node_modules` 解析 `@deepseek-ai/*`（devDependencies 副本），与宿主的实例**不是同一个**——错误码这类依赖 `instanceof` 的东西会退化。功能调试可用，验收用 A。

## 每改一次代码，做什么

| 改动位置 | 需要执行 | 生效方式 |
| --- | --- | --- |
| `src/*.ts`（Host 半） | `pnpm build` | 重启 profile / `--patch` 进程（插件行重新加载） |
| `src/client/index.js`（浏览器半） | `pnpm build` → 刷新页面 | Client Modules 按 bundle 的 mtime/size 判版本，重建即换版本 |
| `test/*` | `pnpm test` | 立即，不需要 harness |
| `docs/*` | — | — |

要点：`lib/` 是入库产物，也是两条回路唯一的加载目标（行指向 `lib/index.js`）。**忘了 build 就会跑到旧代码上**，这是最常见的坑。

## 验证手段（都不用开浏览器）

```sh
# 组合结果对不对：看插件层与最终 config
node apps/cli/lib/bin.js --profile duck --dump-config | Select-String -Context 0,8 duckdb-analytics

# 引擎与工具逻辑：插件自带 86 个用例，用真实 DuckDB，不需要 harness
cd dsh-duck-analytics && pnpm test && pnpm typecheck
```

要跑真实模型（会消耗额度）时用 headless：

```sh
node apps/cli/lib/bin.js --profile duck headless "加载 sales.csv，按月汇总销售额并画折线图"
```

## 三个具体的坑

1. **later layer 替换整段 `config`**，不是深度合并。在 profile 的 `cordis.patch.yml` 里只写 `dataRoot` 是可以的（其余键回落到 schema 默认值），但只要你想改第二项，就得把这项一起写全。
2. **`dataRoot` 相对路径相对启动目录**。bundle 默认 `./analytics-data`，从 harness 根目录启动就解析到 `deepseek-harness/analytics-data`。要么建这个目录，要么在 profile 层覆盖成绝对路径（本次就是这么做的）。
3. **客户端半改完不刷新页面就看不出变化**；HMR 只解决模块替换，不替你重建 bundle。

## 一次性准备 harness

如果 `deepseek-harness` 是新检出的，先让它自己能跑：

```sh
cd deepseek-harness
pnpm install
pnpm build          # 宿主从构建产物加载包；源码启动还需要这一步产出的 lib/
pnpm dsh web        # 或 node apps/cli/lib/bin.js web
```
