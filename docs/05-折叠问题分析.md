# 05 问题分析：图表被折叠进「过程」区

## 现象

图表出现在 tool 调用的结果卡片里。卡片属于 Turn 的**过程区**（process），而过程区在 Turn 结束后会被自动折叠。于是：对话继续往下走，图就跟着一起收起来了。

这不是渲染失败，是**位置放错了**：图表被安放在一个「默认可折叠」的容器里。

## 折叠机制：四层判定

### 1. 节点在分组树里的位置

`packages/client/ui-chat/src/client/contract/group-tree.ts` 定义四层：

```ts
export type ChatGroupTree = 'exchange' | 'input' | 'turn' | 'process'
const DEPTH = { exchange: 0, input: 1, turn: 2, process: 3 }
```

折叠作用在 **process（深度 3）** 这一层。tool 调用与 tool 结果都在这一层。

### 2. 谁决定 Turn 能否折叠

`packages/client/ui-chat/src/client/contract/turn-process.ts:53`：

```ts
export function turnProcessAlwaysOpen(node) {
  const reason = location.turn.end?.data.reason.kind
  return location.turn.status === 'open'
    || reason === 'aborted' || reason === 'interrupted' || reason === 'error'
}
```

只有「还在跑 / 被中止 / 被打断 / 出错」的 Turn 强制展开。**没有任何按工具内容豁免的口子**——所以插件无法声明「我这个工具结果要一直可见」。

### 3. 呈现策略（可配置）

`packages/client/ui-chat/src/client/presentation-policy.ts`：

| 模式 | `foldCompletedTurns` | `stepGrouping` |
| --- | --- | --- |
| compact | true | collapsed |
| standard | true | collapsed |
| **detailed（Web 默认）** | true | history |
| **verbose** | **false** | **none** |

默认模式是 `detailed`（`chat-settings.ts` 的 `DEFAULT_TRANSCRIPT_VIEW_MODE`），即**完成即折叠**。只有 `verbose` 完全不折叠。

### 4. 折叠时机与「最新一轮保持展开」

`stores.ts` 的 `turnProcessOpen(state, spec, defaultOpen)`：读用户显式选择；否则用 `defaultOpen`。而 `defaultOpen` 的来源是（`ChatNodeSeat.tsx:62`）：

```ts
const storedOpen = useStore(state => processSpec !== undefined
  && turnProcessOpen(state, processSpec, bottom === true && deferCollapse))
```

`deferCollapse` 要求 `collapseTiming === 'next-input'`。也就是说：**默认（`completion`）下，Turn 一结束、只要它有内容，过程区立即折叠。** 这解释了为什么图可能"当场就没了"，而不是等到下一句。

## 对照组：action-cards 为什么不会被折叠

`packages/experimental/client-ui-action-cards` 的卡片出现在回答之后且不被折叠，做法是两个关键点：

1. 它注册的是 `conversation.chat.turnTail`，不是 `tool.call.toolview`；
2. 承载它的节点 `turn-tail` 在 `conversation-nodes/turn-tail.ts:138` 明确写着 `groupTree: 'turn'`——**深度 2，在 process 之外**。

而 `contract/slots.ts:492` 声明：

```ts
'conversation.chat.turnTail': { kind: 'list', scope: 'session', owner: TurnTailOwnerProps }
```

`kind: 'list'` 意味着多个插件可以各自注册一条，**不会与 action-cards 冲突**（对比 `tool.call.toolview` 是 `keyed`，一个 key 只能有一个占用者）。owner props 是：

```ts
export interface TurnTailOwnerProps {
  turn: TurnLocation
  seq: number
  openFile: (path: string) => void
}
```

## 结论

| 位置 | 深度 | Turn 结束后 | 是否适合图表 |
| --- | --- | --- | --- |
| `tool.call.toolview`（最初） | process (3) | 默认折叠 | ✗ 藏在过程区里 |
| 自定义会话节点（`conversation.chat.node` + `groupTree: 'turn'`） | turn (2) | 保持可见 | ✓ **本次采用** |
| `conversation.chat.turnTail` | turn (2) | 保持可见 | ✓ 位置对，但 owner props 不含数据，需额外注入 |
| 助手正文 markdown |－| 保持可见（`foldedReplies: 'all'`）| 只能放静态文本，不能交互 |

图表需要交互，所以最后一行不可行；第一行是问题所在；**会话节点既有 turn 深度、又自带数据，是唯一不依赖外部状态的方案**。

## 三个可选方案

### 方案 A：改设置（零代码，立即可用）

把「工作详情」模式改为 **Verbose**（`foldCompletedTurns: false`），或把折叠时机改为 **next-input**（最新一轮保持展开，直到你发下一条）。

- 优点：立刻生效，无需构建。
- 代价：**全局生效**——所有工具调用、推理过程都不再折叠，转录会变得很长。这是「用整页的信息密度换一张图」，不适合作为长期方案。

### 方案 B：把图表搬到 turn tail（推荐）

在 `conversation.chat.turnTail` 注册一个 list 条目，与 action-cards 并列，渲染本 Turn 的图表；tool 卡片回归纯文本结果。

- 优点：位置正确（回答之后、过程之外）、保持可见、可交互、不依赖用户改设置、不与其它插件冲突。
- 代价：**数据来源要重新解决**。tail 只拿到 `turn`/`seq`，拿不到 tool 结果；需要一条读取本 Turn 图表元数据的通路。两条路：
  - **B1 session projection**（仓库认可的做法）：Host 侧注册一个投影，把每个 Turn 最后一条 `dsh-duckdb-chart` 元数据折叠出来；客户端从投影读。符合「model-visible ⟺ logged」，且回放天然可用。
  - **B2 客户端读事件**：用 `ctx.sessions` 拿会话快照，扫本 Turn 的 `tool/result` 事件取 `meta`。少写一个投影，但要客户端自己解析事件流，且要处理窗口截断。

### 方案 C：双处渲染

tool 卡片保留图表（展开时可见），同时在 turn tail 放一个精简版（标题 + 图）。

- 优点：改动最小，不依赖投影。
- 代价：同一份数据两处渲染，需要两套尺寸/交互取舍；用户可能疑惑「为什么有两张图」。

## 选择：自定义会话节点

三条路的取舍：

1. **会话节点**（采用）：`ConversationNodeDefinition` 是 DSH 公开的扩展点，节点自己携带 `data`，`match/start/update` 从日志事件重建，因此回放与实时同源；把 `groupTree` 设为 `turn` 就落在折叠区之外。
2. **turnTail + 投影**（试过，失败）：tail 的位置也对，但它只给 `turn`/`seq`/`openFile`，数据得靠渲染期反查会话投影；那条注入路径没拿到会话时组件只能静默返回 `null`，表现为"依然只有工具面板里有图"。
3. **改设置**（不采用）：Verbose / next-input 能让过程区不折叠，但那是全局的——用整页信息密度换一张图。

## 已实施：自定义会话节点（官方接口）

第一版尝试走 `conversation.chat.turnTail` + session projection，**没有生效**：tail 的 owner props 只有 `turn`/`seq`/`openFile`，数据只能靠 `inject(sessionId)` 拿投影，而该注入在那个渲染路径上没拿到可用会话，组件静默返回 `null`（我的失败设计不报错，所以只表现为"没有图"）。

改用 DSH 官方提供的**会话节点**扩展点，数据随节点自带，不需要投影：

- 接口：`ConversationNodeDefinition`（`packages/client/ui-conversation/src/client/contract/conversation.ts:213`）——`kind` / `target` / `match` / `start` / `update` / `publication` / `buildViewNode`；
- 注册：`ctx.uiConversation.events.register(definition)`（与 `turn-tail`、`tool-call` 同一套机制）；
- 视图：keyed slot `conversation.chat.node` 按节点 `kind` 分发；
- 位置：节点自报 `groupTree: 'turn'`，落在 **turn 深度**，不在可折叠的 process 组里。

### 定义要点

| 项 | 值 | 理由 |
| --- | --- | --- |
| `kind` | `duckdb-chart` | 与 `tool-call` / `turn-tail` 等并列，不冲突 |
| `target` | `chat` | 交给 chat 渲染面 |
| `match` | `tool/result` 且 `meta` 通过 `readChartMeta` | 只吃自己的元数据；`chart: null` 的纯文本查询**不建节点** |
| 节点身份 | `turn-<n>` | 一个 Turn 一个节点 |
| `start` / `update` | 记录 `{ turn, seq, meta }`，后来的结果覆盖 | 天然实现"只显示该 Turn 最后一张图" |
| `buildViewNode` | `anchorSeq = seq`，`groupTree: 'turn'`，`data = { turn, meta }` | 位置紧跟产生它的工具行，且在折叠区之外 |
| `publication` | 默认（immediate） | 结果一落盘就出现在消息区，不必等 Turn 结束 |

关键收益：**节点携带自己的数据**。日志里本来就有 `tool/result.meta`，`match/start/update` 从事件重建状态，所以刷新与回放会重建同一个节点，不需要投影、不需要 `presentationMeta` 之外的新通道。

### 保住了什么

| 场景 | 结果 |
| --- | --- |
| Turn 运行中 | tool 卡片里的实时图 + 消息区的图表节点 |
| Turn 结束、过程折叠 | **消息区的图表节点仍在** |
| 刷新/回放 | 由日志事件重建节点，画同一张图 |
| 未画图的查询 | 不匹配，不出现空节点 |
| 一个 Turn 内多次画图 | 节点被更新，只显示最后一次 |

tool 卡片保留图表：它是运行期能紧跟参数与文本结果的现场视图；消息区节点是长期可见的那一份。Turn 结束后卡片随过程收起，视觉上只剩消息区一张。

| 编号 | 验收项 | 证据 |
| --- | --- | --- |
| F1 | 只匹配本插件的图表元数据 | `test/client-bundle.test.ts`「matches only chart-bearing tool results」 |

## 未采纳的替代与理由

**方案 A（改设置）**：把「工作详情」改为 Verbose 或折叠时机改为 next-input 也能立刻看到图，但它是**全局**的——所有工具调用与推理都不再折叠，等于用整页信息密度换一张图。作为排障手段有用，不是产品解。

**turnTail + 投影（第一版尝试）**：这正是"问题依旧"的原因。tail 的 owner props 不含数据，读取端要额外注入会话投影，而该注入在 turnTail 渲染路径上没有拿到可用会话；组件为不崩卡片而静默返回 `null`，于是表现为"依然只有工具面板里有图"。教训：**优先用节点自带的 `data`，而不是在渲染期去反查别处的状态**。

**客户端读事件（B2）**：把"哪些事件算数"的规则搬到浏览器，回放与实时容易分叉，还要自己处理事件窗口截断。规则留在节点定义里更稳。
