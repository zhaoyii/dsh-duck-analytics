# 01 设计评审：原稿的问题与修正

评审对象是 `DeepSeek-Harness-DuckDB-Analytics-Design.md`（下称「原稿」）。证据来自本仓库 `deepseek-harness` 检出（0.2.2-rc.3）的源码与文档，以及在本机 DuckDB 1.4.x 上的实测。

结论先说：**原稿的架构判断正确，工程契约错误**。它选对了机制（Agent 作用域数据库、`presentationMeta` 持久化卡片元数据、keyed toolview slot），但在类型契约、安全边界、抽象层次、以及「scratch 插件能做什么」这四件事上给出了不可用的方案。

## A. 会直接导致失败的错误

### A1 `output.schema` 用了 JSON Schema，而契约是 `ValueSchemaSpec`

原稿第 5 节、6.6 节的 `RESULT_SCHEMA` 里出现 `type: ['object', 'null']`、`columns: { type: 'array' }`（无 `items`）、对象节点缺 `additionalProperties`。这些在 `ValueSchemaSpec` 里都不成立。

证据：`packages/core/tools/src/schema.ts` 定义 `ValueSchemaSpec` 为闭合联合（`StringValueSchemaSpec | … | ObjectValueSchemaSpec | JsonValueSchemaSpec | OneOfValueSchemaSpec`），其中 `ObjectValueSchemaSpec.additionalProperties: boolean` 是必填字段，可空只能用 `oneOf: [A, B]`（至少两个分支）。`type` 不接受数组。

影响：`defineTool` 在注册时编译 schema，这些写法会直接抛错，插件加载失败。

修正（已实现）：输出 schema 用 DSL 写；「任意结构的行」用 `{ type: 'object', additionalProperties: true }` 表示，而不是 `{ type: 'json' }`——后者推断为 `JsonValue`，会让 `rows` 的元素类型退化成任意 JSON，丢失 `Record<string, JsonValue>` 的约束（`src/tools.ts` 的 `ROW`）。

### A2 客户端卡片不是「加一个包」就能出现

原稿 7.1 节说 `pnpm add echarts echarts-for-react`，7.2 节给出 slot 注册，8.3 节给出 client package.json，然后假定卡片就能出现。缺了三样东西：

- `package.json` 里的 `dsh.client` 声明（`platform: 'web'` + `inject`）；
- 构建产物 `lib/client.js`；
- 该包作为 Loader 条目被启用。

证据：`packages/client/modules/README.md`（原文 `packages/web/client-modules`，包已迁到 `packages/client/modules`）——「the host serves built client bundles, so `pnpm run build` must have produced each `lib/client.js` before launch; a missing bundle fails activation loudly」；客户端 bundle 走懒加载 CJS 工厂协议。

影响：原稿把卡片写成「加依赖 + 注册 slot」两步，实际还缺**bundle 产物与清单声明**两项，照抄会得到一个不渲染任何东西的插件。

修正（已实现）：ECharts 卡片已按正确的三件套交付（`dsh.client` 声明、`lib/client.js`、Loader 条目复用），见 [04 文档](04-图表卡片-ECharts.md)。原稿真正缺的是「bundle 必须存在且 id 必须等于包名」这条规则；它没有说，也没有给出离线生成的方式。

### A3 错误类型不符合工具错误约定

原稿全程 `throw new Error('...')`（`database.ts`、`file-loader.ts`、`query-engine.ts`、`install-agent-tools.ts`）。

证据：`packages/core/tools/src/pipeline.ts` 的 `errorInfo()` 只在 `error instanceof HarnessError` 时保留 `name` 和 `code`；否则工具结果只有一个字符串。

影响：策略层、压缩层、模型都无法按 `code` 路由；日志里也拿不到稳定标识。

修正（已实现）：`src/errors.ts` 定义 `AnalyticsError extends HarnessError` 与三个稳定 code：`ANALYTICS_REQUEST_REJECTED`、`ANALYTICS_TIMEOUT`、`ANALYTICS_ENGINE`。取消路径反过来做：**不包装**，让 `exec.signal` 的 reason 原样抛出（`src/session-database.ts` 的 `#run`），否则执行器无法识别取消。

### A4 `WeakMap`、`datasetId`、`tableName` 三套标识互相打架

原稿同时维护 `datasetId`（模型可见）、`tableName`（SQL 里用）、`WeakMap<Agent, SessionDatabase>`（隔离键），并要求模型在 SQL 里手写 `dataset_<uuid>`。

影响：模型跨轮次必须原样搬运一个 32 位十六进制串，抄错就报「表不存在」；而这张表本来就在该会话独占的库里，不存在跨会话重名问题。

修正（已实现）：取消 `datasetId`。表名本身就是数据集身份，由 Host 从文件名派生（`sales.csv` → `sales`，冲突加 `_2`），保证 `[a-z][a-z0-9_]*` 且只在本会话库内去重。少一个概念、少一类失败。

### A5 生命周期信号没处理全

原稿 6.7 节在 `agent/created` 里 `await installAgentTools(...)`。

证据：`agent/created` 的 `source` 可以是 `'startup' | 'resume' | 'clear' | 'compact'`（`packages/core/agent/src/runtime-types.ts`）。

影响：同一个 Agent 在 `clear` / `compact` 后再次进入初始化路径时，若安装代码注册的是全局工具，就会重复注册并抛错；若每次新建数据库，resume 场景下已加载的表消失且没有提示。原稿对此只在第 15 节写「必须测试」。

修正（已实现）：不监听创建事件。数据库按需创建（首次工具调用），归属由 `exec.agent` 决定，释放挂在 `agent/disposed`；插件卸载时整体释放（`src/index.ts`、`src/session-registry.ts`）。

## B. 抽象层次：过度设计与错误抽象

### B1 每个 Agent 安装一套工具 —— 不必要

原稿把「每会话独立数据库」和「每会话注册工具」绑在一起。二者没有因果关系。

证据：`ToolExecutionInput.agent` 的定义是「The agent on whose behalf the call runs (set by the agent loop)」（`packages/core/tools/src/contracts.ts`）；仓库内 `dsh-tool-todo` 就是全局注册 + `exec.agent.session`（`packages/todo/tool-todo/src/index.ts`）。

修正（已实现）：`ctx.tools.register` 每个工具只调一次，`apply(ctx)` 里完成；会话状态通过 `exec.agent` 解析。

### B2 共享协议包 + 三包拆分 —— 对 MVP 过重

原稿拆 `shared` / `host` / `client` 三个 workspace 包，并为 `ChartSpec` 单独定义一套协议。

影响：MVP 只有 Host 一侧，两端的协议还不存在，此时引入 shared 包只是把 `import` 变长、把类型同步问题提前。

修正（已实现）：单包六模块（`index` / `tools` / `session-registry` / `session-database` / `data-files` / `sql-guard` / `render` / `errors`）。等 Phase 2 真的出现第二个消费端（浏览器）时再抽协议，且那时协议的内容已经被 MVP 的 `presentationMeta` 需求定下来。

### B3 正则黑名单当安全边界 —— 既不安全也不准确

原稿 6.5 节的 `FORBIDDEN` 数组有 17 条正则，并在注释里承认「不是完整边界，生产要用 AST」。

实测漏检（在 DuckDB 1.4.x 上验证）：

| 输入 | 原稿黑名单 | 实际后果 |
| --- | --- | --- |
| `SELECT * FROM 'C:/x.csv'` | 放行（实测） | **直接读文件**：DuckDB 支持字符串字面量作表名 |
| `SELECT * FROM glob('C:/**')` | 放行（实测） | 枚举文件系统 |
| `SELECT read_text('C:/x.txt')` | 放行（函数名不在名单） | 读任意文本文件 |
| `SELECT * FROM sniff_csv('x.csv')` | 放行（函数名不在名单） | 读文件并推断 schema |

实测误杀：`WHERE note LIKE '%drop%'`、列名恰好是 `set`、注释里出现 `create`。

修正（已实现）：两层判定，各管一件事。

1. **语句数交给 DuckDB 自己**：`connection.extractStatements(sql).count === 1`。这是权威 parser，`SELECT 1; DROP TABLE sales` 直接判 2 条。
2. **词法层判定语义位置**：`src/sql-guard.ts` 自己分词（正确跳过 `'...'`、`"..."`、`--`、`/* */`、`$tag$`），只做两件事——首 token 必须是 `SELECT`/`WITH`；表位置（`FROM`/`JOIN`/表列表逗号之后）不得出现字符串字面量，函数调用位置不得出现读取类函数名（`read_*`、`*_scan`、`glob`、`sniff_*`、`st_read`、`parquet_metadata` 等）。

这不是完整沙箱，残余风险与升级路径写在 `03-MVP-设计与实现.md` 的安全一节，并且**不假装它是 AST 校验**。

### B4 「禁用外部文件访问」没有落到可执行的机制

原稿只在文字里要求「禁止外部文件扫描函数」，没有给出机制。我在本机实测了三种看起来可行的机制，结论对设计有决定性影响：

| 机制 | 实测结果 |
| --- | --- |
| `SET enable_external_access = false`（运行时） | 失败：`Cannot change enable_external_access setting while database is running` |
| `DuckDBInstance.create(':memory:', { enable_external_access: 'false' })`（创建时） | **生效**：任何文件读取都报 `Permission Error`，普通建表/查询正常 |
| `SET allowed_directories = ['<root>']` | **不生效**：根外文件仍可被 `read_csv_auto` 读取 |

于是只有两条路：

- **甲**：实例创建即禁文件访问（隔离强），代价是数据必须由 Host 用另一个实例读出来、再经 JS 逐行灌入（DuckDB Node API 的 appender 只提供 `appendX` 系列，没有 `appendRow`，需要自己写逐类型映射；`getRowObjectsJson()` 还会把 `BIGINT` 转成字符串）。
- **乙**：允许文件访问（原稿的隐含假设），安全完全落在 SQL 门禁上。

MVP 选**乙**，理由写在 `02-关系模型.md` 的威胁模型一节：同一 Agent 本来就持有 `read` / `bash`（同一沙箱策略下的文件读取权），DuckDB 读文件不扩大其权限；真正不能破的是「会话间不串数据」「只读」「资源有界」。甲方案作为 Phase 3 的选项保留，并给出了触发条件。

### B5 可调参数写死、配置来源不对

原稿建议 200MB 文件上限、1000 行、15s、`process.env.DSH_ANALYTICS_ROOT`。

证据：仓库约定「凡是不同部署可能需要不同值的参数，都必须定义为配置字段」（`docs/user/develop/basic/config.zh.md`）。

修正（已实现）：七个 Config 字段全部走 Schemastery，默认值在 schema 里，`cordis.yml` 可覆盖；`dataRoot` 缺失或不是目录时**在插件加载时抛错**（`resolveDataRoot`），而不是等到第一次调用。

### B6 用 `xlsx` 转 CSV 再读 Excel

原稿 6.4 节的 `loadExcel`：`XLSX.readFile` → `sheet_to_csv` → 临时文件 → `read_csv_auto`。

问题：日期、前导零、公式、多 Sheet 类型在这一圈里全部丢失或漂移；多一次落盘；多一个依赖（`xlsx` 0.18.5 在 npm 上已停止维护）。

修正（已实现）：MVP 只支持 DuckDB 原生可读的三种格式（CSV/Parquet/JSON），扩展名白名单在 `src/data-files.ts`，拒绝时给出可操作提示。Excel 列到 Phase 2，用 DuckDB 的 `read_xlsx` 扩展或 Host 端解析后导入，二选一，届时再定。

### B7 图表元数据存了两份

原稿既在 canonical value 里返回 `rows`，又在 `presentationMeta` 里再存 `preview`（前 100 行），并宣称「metadata 最多 256KB」。

证据：canonical value 不进durable event——`ToolExecutionSuccess.value` 的注释是「Execution-local canonical value; deliberately omitted from durable events」（`packages/core/tools/src/contracts.ts`）。

影响：`preview` 是「结果行的副本」，不是「画图所需的最小数据」——两者体积差一个数量级，而且噪声在于它把同一批数据用两种形状持久化两次。

修正（已实现）：现在卡片需要元数据了，所以由 [04 文档](04-图表卡片-ECharts.md) 定义 `ChartMeta`：只存点（`{label, value}`）、上限 120 点、超出计入 `omitted`，外加 `kind`/`version` 做版本判别。**不存行对象**，因此载荷与结果规模解耦，256 KB 这种没有执行手段的愿望也就不需要了。

## C. 原稿正确、予以保留的判断

- **用 Agent 作用域作为数据库作用域**：正确，`Agent` 就是会话的运行拥有者，`agent/ctx` 与作用域清理机制确实存在。MVP 只是把「作用域」用于资源归属，而不是工具注册。
- **`output.presentationMeta` 是卡片元数据的正确通道**：正确，`ToolResult.meta` 会随 `tool/result` 持久化并交给 `presentResult` 与客户端（`contracts.d.ts`）。MVP 暂不使用，但通道确认无误。
- **keyed slot `tool.call.toolview` 是 Web 卡片的唯一入口**：正确。`packages/client/ui-slots/src/index.ts` 的 `SlotMap` 声明其为 `kind: 'keyed'`，已有插件用 `ctx.slots.inject('tool.call.toolview', () => ctx.slots.register({ name, key, locale, inject }, Component))` 注册（`packages/client/ui-tool/src/client/tool/toolviews/read-row.tsx`）。原稿 7.2 的调用形状基本正确，只是漏了 `locale`（UI 文案必须走本地化字典，仓库用 `verify-client-ui-i18n` 强制）和 `inject`。
- **内置 Web 客户端不消费 `presentCall` / `presentResult`**：原稿这一点纠对了。`docs/cookbook/adding-a-tool.zh.md` 明确写了「内置 Web Client 不消费 `presentCall` 或 `presentResult`」。Host presenter 仍然有价值（CLI、日志、非 Web 宿主），MVP 的 `render` 同时服务两者，因此不需要它们。

## D. 可验证性问题

原稿第 11 节给了测试计划，但混了「Phase 1 可测」和「Phase 2 才有」的项，也没有给出当前环境能跑的入口：

- 验收表把 A5（图表卡片）、A7（历史回放）与 A1–A4 放一起，导致「MVP 完成」无法判定。本文档把验收拆成 MVP / Phase 2 两张表（见 03 文档）。
- `node --test` 在本仓库里不是测试入口（仓库用 vitest），scratch 场景又没有 vitest 配置；同时 DSH 的文件沙箱不允许测试框架起子进程（`node --test` 会 `spawn EPERM`）。MVP 因此提供单进程测试入口 `test/all.mjs`，并用一个解析钩子把 `@deepseek-ai/*` 映射到仓库构建产物（`test/hooks.mjs`）。
